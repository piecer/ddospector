Claim selects lowest eligible ordinal `ORDER BY ordinal LIMIT 1 FOR UPDATE SKIP LOCKED`; skipping is queue selection only, not a consistent list snapshot [P1]. Global lock is deliberately modest serialization, not a high-throughput claim.
After locks and immediately before decision DML, sample PostgreSQL `clock_timestamp()` as t, not transaction-start `now()` [P2]. Deadline/lease arbitration linearizes at that guarded DML, not response arrival or a promise about fsync latency. No file, pure-task computation, HTTP or other external wait inside the transaction. Final guarded UPDATE must affect exactly one row; otherwise rollback event/result/counters together. Database commit is the visibility/durability boundary, not an earlier SELECT.
Worker token is a fresh UUID per claim, private and never a PID. Every heartbeat, progress, failure and completion verifies state RUNNING/CANCEL_REQUESTED, exact `(run_id,attempt,generation,owner_token)`, and `lease_until > t` inside that transaction. Each claim increments attempt and generation by1 and installs owner/lease=t+10s. Lease renewal does not extend deadline_at: even an unexpired owner must terminalize as TIMED_OUT after the absolute deadline. Requeue or terminal revocation of an owned claim increments generation by1 and clears owner/lease. Queued cancellation/timeout leaves generation unchanged. Thus generation0..6 is reachable across at most three claims; attempt never resets. Terminal releases unfinished slot and, if owned, leased slot, but never retained reservation.

### 5.1 API response deadline and retained custody — S02-BE-C01

- One process-rooted S02 manager owns four slots, its dedicated source executor (max4 threads), and strong references to each operation, underlying executor Future, async coordinator/connect/driver/cleanup tasks and exact connection. Reserve before ANY submission/connection; at most one source submission and one connection acquisition per operation. Queued, executing, detached and retiring owners share max4; no secondary cleanup queue, permit recycling into a replacement manager, default-executor spill or hidden reconnect. Saturation -> immediate RUN_BUSY.
- Request waiting uses a deadline notification independent of owned task retirement (non-cancelling wait over retained tasks); cancellation of its await is not a done/retired witness [C-P1,C-P2]. At expiry, ASGI cancellation, disconnect or shutdown, atomically latch admission_revoked; no subsequent business statement/COMMIT starts. Already-issued SQL/COMMIT may finish; never assert rollback merely because a response failed. Discard late source output. A still-live transport gets the §4 deadline error promptly without joining work; disconnected transport gets no success claim. Response sending cannot guarantee a disconnected/unschedulable peer receives bytes.
- On normal timely business completion, select the validated response before cleanup. Cleanup failure cannot replace a confirmed committed result with a false rollback claim. HTTP finalization never releases the slot. Retirement starts a separate at-most1s cleanup-observation grace; it is NOT added to the5s response deadline. Grace expiry only ends observation, not work, ownership or the slot charge. The custodian remains until actual retirement, consumes late task exceptions and never publishes late business output.
- The executing source thread alone unwinds history, stream/descriptor context managers and its outer RLock acquisition. A cancelled queued Future is retired only when proven never started; an executing Future retires only after the wrapper has actually returned/raised following finalizers. Preserve S01's existing single-close-attempt descriptor policy, including close-then-error; never retry an ambiguous FD close, release RLock cross-thread, change primitives, clean caller paths or modify coordinator/quarantine/ticket state.
- Exact DB disposal: retain a pending connect through completion; if it yields a late connection, immediately retire that same object. Signal cancellation once to outstanding business driver work; retain/observe its actual unwind. Once driver work settles, perform at most one transaction-context rollback if needed, then at most one local close on that object. These are cleanup, never mutation retry; no concurrent use of the handle. A stuck rollback/close stays owned, not a reason to start another close. Retired means no live driver/connect/cleanup task AND no acquired handle remains open (`connection.closed` is true, including a broken connection [C-P4]); an exception alone is not proof. Close-raised-but-closed with settled tasks retires with a secondary diagnostic; closed false/unknown stays charged, never blindly reclosed.
- Retirement callback atomically refunds exactly one slot only when source and DB predicates both hold; request cancellation, done wrappers, garbage collection and cleanup-grace expiry cannot refund. A late normal cleanup may restore capacity; an unconfirmed disposal remains held until explicit operator process recovery. There is no automatic S01 recovery, data deletion/replay or API process kill.
- Shutdown permanently closes this manager's new S02 admission (otherwise-admissible requests -> RUN_DB_UNAVAILABLE), revokes all owners, and observes ONE shared1s grace, not1s per owner. Store exactly one closed <=512byte diagnostic as manager.drain_result and attempt one nonblocking diagnostic write (sink failure never extends grace): `{schema_version:1,kind:"s02_api_drain",outcome,retained_operations,source_pending,db_pending,disposal_unconfirmed}`. Counts0..4, each pending count <=retained_operations (categories may overlap). CLEAN iff all counts zero; otherwise INCOMPLETE. Source pending includes queued/running/unwinding source; DB pending includes connect/SQL/rollback/close; disposal_unconfirmed counts settled tasks with an unproved handle disposition.
- CLEAN allows normal lifespan shutdown. INCOMPLETE raises fixed `RuntimeError("S02_DRAIN_INCOMPLETE")` from lifespan, never reports clean/reusable shutdown; process-rooted manager/owners remain retained and charged even if lifespan returns/fails. No reinitialization in that process. `shutdown(wait=False,cancel_futures=True)` is not termination of running executor work or a guaranteed interpreter exit [C-P1]. No request timeout authorizes killing the whole API. A permanently stuck API needs explicit operator process recovery; an isolated verifier may terminate only its own recorded PID/start identity AFTER saving INCOMPLETE, never count rescue as clean drain.

## 6. State machine, cancel and terminal arbitration

States: QUEUED, RUNNING, CANCEL_REQUESTED, SUCCEEDED, FAILED, CANCELLED, TIMED_OUT; last four terminal, immutable. No implicit completed/paused/unknown state. Unknown values fail closed.

| Current / actor | Condition at guarded t | Atomic next state / event |
|---|---|---|
| none / admission | Valid new request and reservations | QUEUED / QUEUED; attempt=generation=step=0, started/finished/cancel=null |
| QUEUED / worker | t<deadline, attempt<3, leased_count<2 | RUNNING / CLAIMED; new claim tuple, step=0, first started_at=t |
| RUNNING / owner | Valid claim, no cancel, t<deadline | step0->1 SNAPSHOT_VERIFIED; step1->2 MANIFEST_COMPILED; state stays RUNNING |
| RUNNING / owner | Valid claim, no cancel, t<deadline, step=2, valid result | SUCCEEDED / SUCCEEDED, result+terminal committed together |
| RUNNING / owner | Valid claim, no cancel, t<deadline, deterministic failure | FAILED / FAILED with frozen failure_code |
| QUEUED / cancel | t<deadline | CANCELLED / CANCELLED reason BEFORE_CLAIM; cancel_requested_at=t |
| RUNNING / cancel | t<deadline, lease_until>t | CANCEL_REQUESTED / CANCEL_REQUESTED; cancel_requested_at=t, owner retained |
| RUNNING / cancel | t<deadline, lease_until<=t | CANCELLED / CANCELLED reason LEASE_REVOKED; cancel_requested_at=t, fence revoked |
| CANCEL_REQUESTED / owner | Valid unexpired claim, computation quiesced | CANCELLED / CANCELLED reason WORKER_ACK; even if deadline elapsed |
| CANCEL_REQUESTED / reaper | lease_until<=t | CANCELLED / CANCELLED reason LEASE_REVOKED; even if deadline elapsed |
| RUNNING / reaper | lease_until<=t, t<deadline, attempt<3 | QUEUED / REQUEUED reason LEASE_EXPIRED; revoke, step=0 |
| RUNNING / reaper | lease_until<=t, t<deadline, attempt=3 | FAILED / FAILED reason RETRY_EXHAUSTED; revoke |
| QUEUED or RUNNING / reaper or cancel; RUNNING / valid owner | t>=deadline, no previously committed cancel request | TIMED_OUT / TIMED_OUT reason DEADLINE_EXCEEDED; revoke if owned |
| terminal / any; CANCEL_REQUESTED / repeated cancel | Already committed | No change/no additional event; terminal returned truthfully; pending cancel remains202 |

All other transitions forbidden. Worker heartbeat in RUNNING renews only before deadline; CANCEL_REQUESTED heartbeat acknowledges cancellation rather than extending a lease. Completion/failure first verifies owner; then committed cancel takes priority, then deadline, then success/failure. API cancel applies terminal -> existing cancel -> elapsed deadline -> queued/running rules. Reaper applies terminal -> pending cancel expiry -> deadline -> ordinary lease expiry. Therefore lock winner defines cancel-vs-completion; cancel committed first forbids success; terminal committed first is sticky. Late/stale completion cannot override cancellation, retry, timeout or any terminal result.
FAILED failure_code is exactly SNAPSHOT_INVALID, OFFLINE_PREPARATION_FAILED, RESULT_LIMIT_EXCEEDED or RETRY_EXHAUSTED; TIMED_OUT uses DEADLINE_EXCEEDED; all other states use null. started_at is null iff attempt=0; only owned states have owner/lease; terminal iff finished_at non-null; cancel_requested_at is non-null iff state CANCEL_REQUESTED/CANCELLED. Failed decode never fabricates a valid snapshot/result.
`Event = {seq,at,type,state,attempt,generation,reason}`; seq1..16, at Time, after-transition state/counters. type is QUEUED, CLAIMED, SNAPSHOT_VERIFIED, MANIFEST_COMPILED, CANCEL_REQUESTED, REQUEUED, SUCCEEDED, FAILED, CANCELLED, TIMED_OUT. reason=null except REQUEUED=LEASE_EXPIRED, FAILED=failure_code, TIMED_OUT=DEADLINE_EXCEEDED, CANCELLED=BEFORE_CLAIM/WORKER_ACK/LEASE_REVOKED. Transition and event have one transaction timestamp; no free-form logs in events.
Per attempt, progress events occur once and only after that actual pure step finished; retries recompute and may append their own progress. Maximum normal trace is14 events (admit1 + claims3 + step events6 + requeues2 + cancel request1 + terminal1); reserve16 slots. Heartbeats/polls/duplicate requests emit none. An impossible persisted count/step combination is corruption, not permission to drop history to fit.
CANCEL_REQUESTED means durable intent, not stopped work. CANCELLED means queued work was withdrawn or durable publication authority was revoked/acknowledged. It does not assert a SIGKILL, remote stop or that stale pure CPU work never briefly overlapped after lease expiry. Such work has no external effects and cannot publish. Computation may repeat; no exactly-once side-effect claim.
